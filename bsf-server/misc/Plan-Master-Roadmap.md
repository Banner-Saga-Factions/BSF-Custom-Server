# BSF Server — Master Roadmap

_The single live plan to follow (created 2026-07-02). It reconciles three older, overlapping plans — now archived in the maintainer's local history — into one ordered backlog. When this doc and an archived plan disagree, **this doc wins.**_

## How to use this doc

- **Pick the next item from the phase order below.** Each backlog row names its GitHub issue and, where one exists, a companion plan file — that issue/plan is the spec.
- **One branch per item, off an updated `main`** (repo convention). Each item is its own explain-then-`y` approval cycle per [`../CLAUDE.md`](../CLAUDE.md) working style.
- **Keep it current:** when an issue closes, strike its row; when a new issue is filed, add one. This doc tracks *ordering and dependencies* — it does not restate each item's spec (that lives on the issue).

## Context — why this exists

Three server plans had accumulated and drifted, marking shipped work as "todo" and disagreeing on order:

- **`Plan-Integrate-Original-Stoic-Server.md`** — port 2013 Stoic features to parity. Milestones **M0–M3b shipped**.
- **`Plan-Issue-Triage-2026-06-10.md`** — ordered issue backlog. **Waves 0–2 shipped.**
- **`Plan-PR-134-139-Review-And-Rebuild-Roadmap.md`** — retrospective review of the merged PRs; its findings are now issues #144/#145/#146/#140.

All three optimize **2013 feature parity + correctness**. A newer plan — [`Plan-Reengagement-Sprint-1.md`](Plan-Reengagement-Sprint-1.md) — argues the binding constraint is **matchmaking liquidity** (≈0 concurrent players), implying a different order. This master plan resolves that tension with a **blended sequence**: clear the small correctness/security fixes first (they de-risk everything), then run player-visible features **and** server-side re-engagement wins in parallel, deferring the heavy parity work. Scope is the **server backlog + server-side re-engagement** — no client-recompile work sits in the linear sequence (the spearman cluster and the AI-bot backstop run as separate tracks).

### The disaster-recovery drill (2026-09-02) — finished

**Until this date nobody had ever restored one of our backups, and nobody had followed the deployment
guide on a machine other than the one it was written on.** Both are things an emergency needs to work
first time, and the cheapest moment to find out they do not is while nothing is on fire. So a second
server was built from nothing on a separate Google account, the newest stored backup was restored into
it, and a game client on the open internet signed in as a player who had never existed on that machine.

**It worked, and it needed help.** Fifteen faults were found by *running* the guide rather than
reading it — two of which no earlier review had predicted, because they are only visible when the
guide is run somewhere other than where it was written. **Twelve of the fifteen were mistakes in the
guide**, and those are corrected in [`../docs/Deployment.md`](../docs/Deployment.md) (**PR #238**),
which now also says which parts of itself have been run and which have not. _(Corrected 2026-09-04:
this used to say "fifteen mistakes in the guide … all fifteen are corrected in Deployment.md", and
neither half held. The other three were somewhere else entirely — a wrong citation in
[`../docs/idea-triage.md`](../docs/idea-triage.md), a settings example that pointed new servers at
the live backup store, and the drill's own conclusion, which was itself wrong; see below.)_

**And then the drill turned out to have got something wrong itself.** A four-agent review was still
running when PR #238 merged, and it found more (**PR #239**) — but the one that mattered was not in
the guide at all. It was in the drill's own finding. Two bytes near the front of a database file had
been read as saying whether a copy stands on its own; they only record which of two ways the
database keeps its recent changes. Because the server switches every database it opens into the
second way, **anything lifted from a running server reads the same whether or not it is intact**, so
a checker built on that reading calls every healthy production database damaged. The wrong rule
spread from the drill's notes into a merged pull request and a saved note within a day, and nothing
refuted it until somebody ran the *healthy* case as well as the broken one. **The useful half
survived and is kept**, because it was reproduced twice: the ordinary health check reports a database
whose companion log went missing as perfectly fine when it is in fact empty — our oldest stored copy
is exactly that.

None of this makes the drill a failure; it restored a player onto a machine built from nothing, which
is what it set out to prove. The point of recording it is narrower and worth stating plainly: **an
exercise that finds fifteen faults is not thereby right about its own findings**, and a rule worked
out under pressure travels faster than the check that would have caught it.

It closed no backlog issue and **filed two**. The backup store and the server's public name are each
held by one person, so a second person can build the machine but can neither recover the data
(**#236**) nor answer on the address (**#237**). Both are decisions with a real security cost rather
than defects, so they are recorded rather than settled.

**Still not covered:** pointing a name at the machine, the certificate that depends on it, and a real
upload to the backup store. The drill skipped all three deliberately, so we have no evidence either
way and the guide must not imply we do.

**Phase 1b — two small fixes to what we answer with — DONE (2026-08-25).**

Both are cases where the code we send leaves the player stuck with no way out, and both were surfaced
by the contract track. They are **not** the same defect as **#171** and **#181** — those two replaced an
answer the game re-sends forever with one it accepts. These two are about an answer that strands the
game instead of looping it. Both are small, and both are player-visible.

1. ~~**#176**~~ — shipped. **Two things the work corrected about this row.** A single error-handling
   middleware could not have fixed it: Express 4 catches a handler that fails immediately but never
   sees an `async` one reject, so nothing would ever have reached the middleware. Every router is now
   built by `asyncRouter()`, which routes the failure to a catch-all that answers `409`. And the
   issue text had the mechanism backwards — it said silence produces a retry loop; it produces an
   invisible stall, which is worse. The roadmap row was right and the issue was not.
2. ~~**#180**~~ — shipped, with one guard the row did not anticipate. A flat `401` would have signed
   healthy players out: the unit-variation route puts a lobby id in the last part of the address, so
   the gate reads a number, finds no session, and would have disconnected a perfectly connected
   player for recolouring a unit. The gate now answers `401` only for a segment shaped like a
   session key (32 hex characters) and keeps `403` for anything else. **Settled by measurement, 2026-08-25.** Recovery replays the client's whole boot path rather than
   restoring the screen the player left, so it obeys the original launch arguments. Run twice, one
   variable changed: with `--versus_start` (which both local launchers bake in) the recovered client
   re-queued itself for a **RANKED** match unasked; without it, the same restart recovered to the main
   menu and queued nothing. So this is a local-testing trap, not something a player meets — but it is
   a sharp one, because the re-queue is silent and RANKED costs Elo.
