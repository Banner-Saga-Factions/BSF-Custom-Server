# Key Gotchas

> **Human-facing / operational gotchas live in [`docs/FAQ.md`](../../docs/FAQ.md).** This file owns the **deep protocol / security / persistence traps** that cause real bugs when editing `src/` (they auto-load into agent context here). Keep each fact in one place — operational gotchas in `FAQ.md`, deep traps here — and when you add a trap here, add a one-line title to FAQ's *Deep traps* index. Don't copy prose between the two.

- **Session key `"11"`** is the hardcoded bypass for unauthenticated login — any other value requires a valid session.
- **Express strips the `/services` prefix** inside `ServiceRouter` — path checks must use `/session/...` not `/services/session/...`.
- **The client re-sends failed requests by itself — make mutations replay-safe, and never answer a permanent "no" with `404` or `5xx`.** `HttpAction.canRetry` retries when the response code is `0`, `404`, or `>= 500`, after `resendOnFailDelayMs` (1–2 s). **Carve-out:** `canRetry` itself excludes a maintenance reply (a `503` whose body contains `Offline for Maintenance` or `game_rebooting`) — the test checks `isMaintenance` *before* the code, and `GameFsm` separately aborts the txn and shows a dialog. That is the only lever we have from the server side. **There is no attempt counter anywhere** — a retry ends only when something calls `abort()`, and coverage is thin. Abort happens only for txns **registered** with a battle state via `addTxn` (`BaseBattleState.handleCleanup`): that covers `ready` / `deploy` / `sync`, and `BattleStateTurnRemote.handleCleanup` aborts the turn query directly. **`move` / `action` / `killed` / `exit` are never aborted by battle-state cleanup, and nothing else reaches them** — except the 401/maintenance path below, which aborts only the txn that received that reply (costs nothing: neither code is retried anyway). **`surrender` has THREE send sites and they differ**: `BattleStateSurrender` extends `BaseBattleState` but never calls `addTxn`, so it escapes cleanup by omission (any new state that forgets `addTxn` inherits the same hole); `BattleFsm.cleanup` builds one inline and retains no reference, so that one genuinely IS outside any state and can never be aborted; and `VersusCancelState`'s **is** aborted in its `handleCleanup`. So neither "outside any state" nor "never aborted" is true of surrender as a whole. **14** menu-driven txns are never aborted either (roster / lobby / leaderboard / tourney / location / variation / IAP / Steam-overlay), so for those it lasts the life of the process. Only `VersusStartMatchTxn` is abortable outright; `ArrangePartyTxn` is aborted solely by the next party change on the same screen. On a `401` or maintenance `503`, `GameFsm.txnProcessedCallback` aborts **only the txn that received that reply** — not everything in flight (it does set `communicator.connected = false`, which stops the poll re-arming). **Three different counts, don't mix them:** 23 classes set `resendOnFail = true`; one is the abstract `BattleTxn_Base`, so **25 concrete classes** retry (`/battle/deploy`, `/battle/ready`, `/battle/sync` inherit it without setting it); and since `LobbyTxn` alone serves six routes (`uninvite`, `join`, `decline`, `exit`, `ready`, `unready`), **30 distinct routes** retry — that last figure is the one that matters when asking which routes can be hammered. The classes: the renown-spending roster routes (`hire`, `promote`, `retire`, `stats/purchase`, `unlock` — but **not** `rename`, which charges 10 and does not opt in), every `BattleTxn*`, all three `Lobby*Txn` classes (= **all 8 lobby routes**), plus `ArrangePartyTxn`, `LeaderboardsTxn`, `GameLocationTxn`, `VersusStartMatchTxn`, `UnitVariationTxn`, `TourneyJoinTxn`, `SessionSteamOverlayTxn`, `IapInfoTxn`.
  - **Fix order — idempotence first.** (1) Make the mutation safe to repeat and return `200` on the repeat: this is what the original did (`UnitRetireSvc.java` never checks the unit exists — it deletes by id, a no-op if already gone, and returns success), and it leaves the player's screen correct because the success path is what refreshes roster + renown. (2) `400` / `403` / `409` for genuinely invalid input. (3) `5xx` only for genuinely transient failures. A `409` stops the loop but leaves the client **stale**, so it is the fallback, not the goal.
  - **Do NOT use `501` for an unbuilt route** — `>= 500` is retryable, so the semantically obvious code is the wrong one. `app.ts`'s session gate did exactly this until 2026-07-30.
  - **Known instances:** `/services/tourney/join` (unbounded — key is the last segment, so it authenticates then matches no router → Express default `404`); **`/services/lobby/join`** (unbounded — `404` on both a missing lobby *and* a non-invitee; **all 8 lobby routes** retry, none abortable, so a restart leaves clients hammering; **fix planned**, `403`/`409`, and it currently contradicts the lobby divergence bullet in `CLAUDE.md`); **any of the five never-aborted battle txns still retrying after battle cleanup** (unbounded — `move`/`action`/`killed`/`exit`/`surrender`, of which the last three are the realistic window; the battle middleware `404`s once the battle is gone at +30 s, both-players-left, or a turn-deadline expiry against a vanished session); `Battle.ts` `/battle/query` `404` (bounded by battle cleanup, but ~**2.5×** the query rate during an opponent timeout — 5 s success re-poll vs 2 s failure retry); `/services/iap/info` (same shape, unreachable today). `/roster/unit/variation` escapes only because its key is **not** last, so auth `403`s first and `403` is not retried — **fix the key position and ship the route in the same change**, or the harmless `403` becomes a `404` loop.
  - **#144 (retire double-refund) is LATENT, not live** — the "two overlapping requests both read and both refund" race **cannot happen today**, but note the mechanism carefully. `query`/`queryOne`/`queryUpdate` in `connection.ts` **do** suspend the caller (they are `async`); what they never do is yield to the event loop — the body is synchronous `node:sqlite`, so the continuation is a microtask and Node drains those before accepting any new request. "Async shells that run straight through" was the *previous*, wrong framing. Two details that matter: the retire handler's read is `session.accountData` (**in-memory**, not a DB read), and the refund is a relative `renown = renown + ?`, so a real overlap would double it silently. **Three** things bring it back: (1) a genuinely async DB layer; (2) anything that pauses added between the roster read and the **in-memory update** — which happens *after* the write, so an `await` placed just after a successful write is *inside* the hazard, not past it; (3) multi-process against one DB file, but only with shared session storage (sessions are per-process today). This has been wrong twice — read **both** `connection.ts` and the retire handler in `roster.ts` before rewriting it; the previous version proved something about the helpers and never opened the handler. #154 (refund = 0) settles the money either way; the live remainder is the retry loop (#164).

- `roster_rows` is the number of barracks **grid rows**; total unit capacity is `roster_rows × 9` (`UNITS_PER_ROW`), capped at `MAX_ROSTER_ROWS = 8`. Only `expandBarracks()` and `upsertAccount()` may write the column — `saveRoster*` helpers must never touch it.
- **32-bit account IDs in all in-game data**: the login-id → `account_id` math lives ONLY in `src/services/auth/accountId.ts` (#146) — `accountIdFromSteamId` (Steam: subtract `STEAM_ID_BASE` with plain `Number` math; smaller ids pass through) and `accountIdFromSnowflake` (Discord: low 30 bits). Import the helpers; never re-inline the math, and never "modernize" the Steam rule to BigInt — its exact rounding is baked into every stored ranking row. The original BSF server used small DB account IDs; the game client constructs entity strings as `{account_id}+{index}+{unit_id}`. Using full 64-bit Steam IDs causes each client to compute different entity strings for the same player, diverging the DJB state hash at turn 0. The login response, `party.user`, `team`, `user_id` in all battle messages, and `aliveUnits` keys all use `account_id`. The DB still stores the full provider-id string in `session.external_id_str` (renamed from `steam_id_str` in #25) — the 64-bit Steam ID for Steam users, the Discord Snowflake for Discord users; `session.user_id` is the Number form and may lose precision above 2^53. Since #140, `addSession` dedupes/evicts sessions on `external_id_str` (the exact provider string, which it now sets itself), NOT the derived `account_id` — two provider ids sharing a derived id must not evict each other; the shared-id residual (same `ranking` row, same in-battle identity) is what keeps #140 open.
- **Session keys are 32 hex chars (128 bits)** since 2026-05-08 (issue #53). Pre-2026-05-08 sessions were 16 chars / 64 bits — don't write code that hardcodes the older width.
- **Session reaper frees the opponent before renown is saved** — when the reaper evicts a mid-battle session, the opponent is immediately freed to re-queue. Renown and the battle result are written to the database a moment later in the background. The writes always complete, but the opponent may receive their "battle finished" message while already back in the queue.
- **Party order matters: `party_ids_json` drives turn order.** When building the `defs[]` array for a battle, lobby PARTY push, or any other player-facing surface, walk `party_ids_json` and look each id up in the roster — do NOT filter the roster by party membership (which silently reorders by roster grid position). Use `buildOrderedPartyDefs(roster, party_ids)` in `src/services/account.ts`; the helper also dedupes and skips unknowns. Issue #71 was caused by `roster.filter(u => party_ids.includes(u.id))` returning units in roster order instead of arrangement order.
- **Stat-purchase deltas can be > 1 _and_ negative.** The AS3 client's `GuiCharacterStats` panel batches every `+`/`-` click into one delta per stat at Confirm time, so a single `/unit/stats/purchase` request often carries cumulative deltas (e.g. `delta=6` for six `+STRENGTH` clicks). The panel **decrements on right-click**, so reallocating points OUT of a stat sends a **negative** delta — this is legitimate, not an error (issue #118; rejecting negatives wiped the player's whole batch and units reverted to default stats in battle). Server bound is `-20 <= delta <= 20` with a "resulting value can't go below 0" floor; `0` is a tolerated no-op (the client adds any interacted stat to its batch, so `+1 then -1` yields `0`). The original server (`UnitStatsSvc.java:88-118`) never checks the delta's sign — it validates the **resulting value** against the per-stat `StatRange`. The real per-stat min/max lives client-side in `StatRange` until those tables are ported server-side.
- **Local 2-client tests need `--versus_start --versus_countdown 0`.** FMOD's ANE only initializes once per machine — the second client launched by `launch-game-2p.ps1` falls back to `NullSoundDriver`. The two clients then take asymmetric resource-load paths: the FMOD-side client loads `common/fmod/character_quality_*.fsb`, whose `FmodSoundDefBundle.fsbLoadedHandler` side effect leaks an item in `GamePage.monitor`. `ScenePage.handleLoaded()` then never re-fires, `doInitReady()` → `setReady()` never runs, the local `POST /services/battle/ready` is never sent, and `BattleStateInit` hangs forever. Workaround patch drafted in **Banner-Saga-Factions/BSF-Client#7** (15s timeout in `BattleStateInit` that force-calls `setReady()`) — not applied because it requires rebuilding the SWF. Production 1v1 between two machines does not appear to trigger this — both clients get real FMOD and either both race or both dodge it.
- **`/battle/killed` counts a death only after BOTH clients report it.** Each client independently reports every kill — its own units dying *and* the opponent's (confirmed by captures `0409_c`/`0432_c`). `Battle.applyKillReport()` tracks a per-entity bitmask keyed by `killedparty` and removes a unit from `aliveUnits` only once every `party_index` has reported it (`bits === killMask`), so one modified client can't fabricate the opponent's losses (#18). The winner is then **server-derived** as the party still holding units — never `req.body.killerparty` (#19). Ported from `BattleMonitor.PartiesKills`. Escape hatch: `BSF_KILL_CONFIRM_SINGLE=true` confirms on the first report. Don't "fix" a test that sends one `/killed` and expects the unit gone — it now needs reports from both sessions (`confirmKill` in `test/helpers.ts`).
- **Never edit the per-unit `stats` inside the `defs[]` sent with `BattleCreateData` — but the reason is DISPUTED as of 2026-08-10.** The guidance is safe on either reading; the mechanism is not settled, so don't repeat it as fact. **Reading A (the 2026-06-12 measurement):** a unit fights with its *roster* numbers — the client clamps stats against the class definition once, when the roster loads, and never consults the class again during combat, so editing payload stats changes nothing. That is why the "weak units" debug experiment was a silent no-op and was removed. **Reading B (a 2026-08-01 source trace):** each client builds its **own** units from its roster but parses the **opponent's** party from the payload (`SceneLoader.loadFromDef` → `EntityListDefVars.fromJson`; `applyClassStats` fills only *missing* stats and `clampStats` touches only *out-of-range* ones), so an in-range payload stat would be honoured on the opponent's screen — and the two sides would then simulate different battles. Retest pending (Wave 3 of `misc/Plan-Client-Contract-Third-Review-Corrections.md`); see `docs/client-contract.md` → R13. To get short battles for testing, shrink the *party* instead: `/debug/party-limit`. Anything that must really change a unit's strength has to go through the roster (`saveRoster`), not the battle payload. Client-side mechanism: `bsf-client/docs/data-model.md` §5 "Your account and roster" ([local](../../../bsf-client/docs/data-model.md) | [GitHub](https://github.com/Banner-Saga-Factions/BSF-Client/blob/master/docs/data-model.md)).
- **Crediting a unit's `KILLS` stat (#99) additionally requires both clients to report the same `killer`.** Death confirmation (above) keys on the dead `entity`, not the killer, so it alone wouldn't stop a lone modified client from funneling its confirmed kills onto one favored unit to over-promote it. `applyKillReport()` records the killer the **first** report names (`Battle.killReportKillers`) and only bumps `unitKillCounts[killerparty][killer]` when the **confirming** report names the same killer (a mismatch logs `kill credit skipped: killer mismatch` and credits no one — but the death still confirms, so the battle never stalls). At endgame each side's tally is applied to **its own** roster via `saveRoster`, so a tally can only ever raise the killer-party's own units. **Residual limit:** two *colluding* modified clients can still agree on a false killer — the server can't tell without re-simulating the battle (the same unclosable trust boundary as death confirmation). `BSF_KILL_CONFIRM_SINGLE=true` reverts to trusting the single report's killer.
