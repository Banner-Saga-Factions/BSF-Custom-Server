# Key Gotchas

> **Human-facing / operational gotchas live in [`docs/FAQ.md`](../../docs/FAQ.md).** This file owns the **deep protocol / security / persistence traps** that cause real bugs when editing `src/` (they auto-load into agent context here). Keep each fact in one place — operational gotchas in `FAQ.md`, deep traps here — and when you add a trap here, add a one-line title to FAQ's *Deep traps* index. Don't copy prose between the two.

- **Session key `"11"`** is the hardcoded bypass for unauthenticated login — any other value requires a valid session.
- **Express strips the `/services` prefix** inside `ServiceRouter` — path checks must use `/session/...` not `/services/session/...`.
- **Build routers with `asyncRouter()`, never `Router()`.** Express 4 catches a handler that fails *immediately* but never sees an `async` one reject — so before #176 an async failure sent **no reply at all**, and the game has no request timeout of its own (the five-second one it declares is never started), so it waited for ever showing the player nothing. `src/http/asyncRouter.ts` wraps every handler so the failure reaches the catch-all in `app.ts`, which answers `409`. A new file that reaches for `Router()` out of habit opts silently back out of that.
- **The client re-sends failed requests by itself — make mutations replay-safe, and never answer a permanent "no" with `404` or `5xx`.** `HttpAction.canRetry` retries when the response code is `0`, `404`, or `>= 500`, after `resendOnFailDelayMs` (1–2 s). **Carve-out:** `canRetry` itself excludes a maintenance reply (a `503` whose body contains `Offline for Maintenance` or `game_rebooting`) — the test checks `isMaintenance` *before* the code, and `GameFsm` separately aborts the txn and shows a dialog. That is the only lever we have from the server side. **There is no attempt counter anywhere** — a retry ends only when something calls `abort()`, and coverage is thin. Abort happens only for txns **registered** with a battle state via `addTxn` (`BaseBattleState.handleCleanup`): that covers `ready` / `deploy` / `sync`, and `BattleStateTurnRemote.handleCleanup` aborts the turn query directly. **`move` / `action` / `killed` / `exit` are never aborted by battle-state cleanup, and nothing else reaches them** — except the 401/maintenance path below, which aborts only the txn that received that reply (costs nothing: neither code is retried anyway). **`surrender` has THREE send sites and they differ**: `BattleStateSurrender` extends `BaseBattleState` but never calls `addTxn`, so it escapes cleanup by omission (any new state that forgets `addTxn` inherits the same hole); `BattleFsm.cleanup` builds one inline and retains no reference; and `VersusCancelState`'s **is** aborted in its `handleCleanup`. So neither "outside any state" nor "never aborted" is true of surrender as a whole. **14** menu-driven txns are never aborted either (roster / lobby / leaderboard / tourney / location / variation / IAP / Steam-overlay), so for those it lasts the life of the process. Only `VersusStartMatchTxn` is abortable outright; `ArrangePartyTxn` is aborted solely by the next party change on the same screen. On a `401` or maintenance `503`, `GameFsm.txnProcessedCallback` aborts **only the txn that received that reply** — not everything in flight (it does set `communicator.connected = false`, which stops the poll re-arming). **Three different counts, don't mix them:** 23 classes set `resendOnFail = true`; one is the abstract `BattleTxn_Base`, so **25 concrete classes** retry (`/battle/deploy`, `/battle/ready`, `/battle/sync` inherit it without setting it); and since `LobbyTxn` alone serves six routes (`uninvite`, `join`, `decline`, `exit`, `ready`, `unready`), **30 distinct routes** retry — that last figure is the one that matters when asking which routes can be hammered. The classes: the renown-spending roster routes (`hire`, `promote`, `retire`, `stats/purchase`, `unlock` — but **not** `rename`, which charges 10 and does not opt in), every `BattleTxn*`, all three `Lobby*Txn` classes (= **all 8 lobby routes**), plus `ArrangePartyTxn`, `LeaderboardsTxn`, `GameLocationTxn`, `VersusStartMatchTxn`, `UnitVariationTxn`, `TourneyJoinTxn`, `SessionSteamOverlayTxn`, `IapInfoTxn`.
  - **Fix order — idempotence first.** (1) Make the mutation safe to repeat and return `200` on the repeat: this is what the original did (`UnitRetireSvc.java` never checks the unit exists — it deletes by id, a no-op if already gone, and returns success), and it leaves the player's screen correct because the success path is what refreshes roster + renown. (2) `400` / `403` / `409` for anything that will not change on a second attempt. (3) `5xx` only for genuinely transient failures. A `409` stops the loop but leaves the client **stale**, so it is the fallback, not the goal. `401` is never re-sent either, but it is not a general-purpose refusal: it means *you are logged out* and makes the game disconnect and sign in again, so use it only for that.
  - **Do NOT use `501` for an unbuilt route** — `>= 500` is retryable, so the semantically obvious code is the wrong one. `app.ts`'s session gate did exactly this until 2026-07-30.
  - **Known instances:** `/services/tourney/join` (unbounded — key is the last segment, so it authenticates then matches no router → Express default `404`); **`/services/lobby/join`** (fixed 2026-08-18 — was `404` on both a missing lobby *and* a non-invitee, now `409` (room gone) / `403` (not invited); **all 8 lobby routes** retry and none is abortable, so keep both codes off `404`); **any of the five never-aborted battle txns still retrying after battle cleanup** (unbounded — `move`/`action`/`killed`/`exit`/`surrender`, of which the last three are the realistic window; the battle middleware `404`s once the battle is gone at +30 s, both-players-left, or a turn-deadline expiry against a vanished session); `Battle.ts` `/battle/query` `404` (bounded by battle cleanup, but ~**2.5×** the query rate during an opponent timeout — 5 s success re-poll vs 2 s failure retry); `/services/iap/info` (same shape, unreachable today). `/roster/unit/variation` escapes because its key is **not** last: the gate reads the trailing `lobby_id`, and since #180 it answers `403` rather than `401` for a segment that is not shaped like a session key — deliberately, so that recolouring a unit does not sign a healthy player out. `403` is not retried. **Fix the key position and ship the route in the same change**, or the harmless `403` becomes a `404` loop.
  - **#144 (retire double-refund) is LATENT, not live** — the "two overlapping requests both read and both refund" race **cannot happen today**. #154 (refund = 0) settles the money either way; the live remainder is the retry loop (#164).
  - Full requirement list: [`docs/client-contract.md`](../../docs/client-contract.md) → R10.
- **The friends list only ever grows on the client, so never send a partial one and never send the singular `FriendData`.** The game merges an incoming `tbs.srv.data.FriendsData` by `id` and has **no delete path at all** — a name we have sent can never be removed from that player's screen, and a shorter list is read as an addition rather than a replacement, silently leaving stale names in place. Always send the whole list (`buildFriendsData` in `src/services/friends.ts`). To make somebody un-invitable, send `tbs.srv.data.FriendOnlineData` with `online: false`: the row greys and the invite button answers *"X is currently offline"* and sends nothing, which is also why `online` has to be correct or the feature is simply dead. **Do not send `tbs.srv.data.FriendData` (singular) — ever.** The game handles that class, but for an `id` it already holds it looks the incoming object up in its own list, fails to find it because the object is freshly built, and writes to index −1. The list is growable; it throws because it is a **typed** list, where any out-of-range index is an error rather than a silent no-op. The throw lands before both places that re-arm the long poll, so it does not merely lose that batch of messages — **the client stops polling altogether**. Three fields are load-bearing on top of that: `id` must be the friend's 32-bit `account_id`, and keep it above zero (the game hands it straight back as the target of `/services/lobby/invite`; anything ≤ 0 renders greyed as "not a player" — still clickable, since only `online` blocks an invite), `display_name` must not be null (the list's sort throws and nothing draws), and `avatar64` or `avatar32` must be a non-empty string (the resource loader throws part-way down the list, and the row's placeholder graphic is hidden so a failed load just leaves a blank). Shapes and reasons: [`docs/dataStructures.md`](../../docs/dataStructures.md#friends-list).
- **Never tell the game about a queue it does not know — it stops polling altogether.** `REPORTED_QUEUE_MODES` in `src/const.ts` lists QUICK, RANKED and TOURNEY, and FRIEND is left out of it for a **hard** reason, not a tidy one. The game registers a counter for exactly those three (`VsMonitor.as:39-41` calls `addType` once each) and then, on every queue update, does `entriesByVsType[type].setPowers(...)` **with no check that the entry exists** (`VsMonitor.as:212-215`). A `tbs.srv.data.VsQueueData` carrying `type: "FRIEND"` therefore throws — inside the same message-dispatch loop that the singular-`FriendData` trap above kills polling from, with the same result: the client stops asking for messages at all. Both `getInitialData` (login) and `notifyQueueUpdate` (after a match) filter on this list. Adding a mode to `GameModes` does **not** mean adding it here.
- **Two reasons the battle map is honoured only for a friendly pair, and the second one affects everybody.** `tryCreateBattle` applies the requested `scene` only when both sides asked for a friend match. The obvious reason is that nobody should pick the ground for a stranger they pulled out of the open queue (#208). The less obvious one: **the game never clears the map it stored.** `GreatHallPage.guiGreathallVersus` sets `SCENE_URL` but leaves `BATTLE_SCENE_ID` untouched, and only `FriendLobbyPage.launchMatch` ever writes it — so after one friend match, every subsequent *quick* match keeps asking for that same old map, for the life of the process. This gate is the only thing stopping it being honoured. Do not lift it while widening the map list (#200).
- **Naming an opponent is honoured even when they never asked for you.** A friend lobby fills in `forcematch` (the chosen opponent) and `scene` (the chosen map) on `/services/vs/start`, and both sides send it, which is how the pair finds each other (#205). But the rule ported from `VsWorker.checkForceMatch` also pairs you with somebody who named **nobody** — so a player waiting in the open queue can be pulled into a battle a stranger arranged, and since #91 every signed-in player's `account_id` is public. Kept deliberately on 2026-08-27 as the reference behaves this way — filed as **#208**; the two guards that make it survivable are that such a battle is **not** friendly (`friendly` needs BOTH sides to have asked for `FRIEND`, `VsWorker.java:705`), so it pays and rates normally, and that the requested map is applied **only** to a friendly battle, so nobody picks the ground for a stranger. **Two traps when editing `queue.ts`:** the force-match test must run **before** `checkWindows` in `findBestMatch` and must exempt the pair from the re-check in `tryCreateBattle` — `threshold_power` starts at 0 and only ever grows to 4, so friends whose parties differ by more than that would otherwise wait on a match that can never be made, with nothing on screen to say why; and `checkForceMatch` is a **deliberate divergence** — the reference's mirror-image branch (`VsWorker.java:789`) tests the wrong side's field and is dead, so we implement the behaviour its comments describe instead of copying the slip.
- **32-bit account IDs in all in-game data**: the login-id → `account_id` math lives ONLY in `src/services/auth/accountId.ts` (#146) — `accountIdFromSteamId` (Steam: subtract `STEAM_ID_BASE` with plain `Number` math; smaller ids pass through) and `accountIdFromSnowflake` (Discord: low 30 bits). Import the helpers; never re-inline the math, and never "modernize" the Steam rule to BigInt — its exact rounding is baked into every stored ranking row. The original BSF server used small DB account IDs; the game client constructs entity strings as `{account_id}+{index}+{unit_id}`. Using full 64-bit Steam IDs causes each client to compute different entity strings for the same player, diverging the DJB state hash at turn 0. The login response, `party.user`, `team`, `user_id` in all battle messages, and `aliveUnits` keys all use `account_id`. The DB still stores the full provider-id string in `session.external_id_str` (renamed from `steam_id_str` in #25) — the 64-bit Steam ID for Steam users, the Discord Snowflake for Discord users; `session.user_id` is the Number form and may lose precision above 2^53. Since #140, `addSession` dedupes/evicts sessions on `external_id_str` (the exact provider string, which it now sets itself), NOT the derived `account_id` — two provider ids sharing a derived id must not evict each other; the shared-id residual (same `ranking` row, same in-battle identity) is what keeps #140 open.
- **Session keys are 32 hex chars (128 bits)** since 2026-05-08 (issue #53). Pre-2026-05-08 sessions were 16 chars / 64 bits — don't write code that hardcodes the older width.
- **Session reaper frees the opponent before renown is saved** — when the reaper evicts a mid-battle session, the opponent is immediately freed to re-queue. Renown and the battle result are written to the database a moment later in the background. The writes always complete, but the opponent may receive their "battle finished" message while already back in the queue.
- **Party order matters: `party_ids_json` drives turn order.** When building the `defs[]` array for a battle, lobby PARTY push, or any other player-facing surface, walk `party_ids_json` and look each id up in the roster — do NOT filter the roster by party membership (which silently reorders by roster grid position). Use `buildOrderedPartyDefs(roster, party_ids)` in `src/services/account.ts`; the helper also dedupes and skips unknowns. Issue #71 was caused by `roster.filter(u => party_ids.includes(u.id))` returning units in roster order instead of arrangement order.
- **Stat-purchase deltas can be > 1 _and_ negative.** The AS3 client's `GuiCharacterStats` panel batches every `+`/`-` click into one delta per stat at Confirm time, so a single `/unit/stats/purchase` request often carries cumulative deltas (e.g. `delta=6` for six `+STRENGTH` clicks). The panel **decrements on right-click**, so reallocating points OUT of a stat sends a **negative** delta — this is legitimate, not an error (issue #118; rejecting negatives wiped the player's whole batch and units reverted to default stats in battle). Server bound is `-20 <= delta <= 20` with a "resulting value can't go below 0" floor; `0` is a tolerated no-op (the client adds any interacted stat to its batch, so `+1 then -1` yields `0`). The original server (`UnitStatsSvc.java:88-118`) never checks the delta's sign — it validates the **resulting value** against the per-stat `StatRange`. The real per-stat min/max lives client-side in `StatRange` until those tables are ported server-side.
- **Local 2-client tests need `--versus_start --versus_countdown 0`.** FMOD's ANE only initializes once per machine — the second client launched by `launch-game-2p.ps1` falls back to `NullSoundDriver`. The two clients then take asymmetric resource-load paths: the FMOD-side client loads `common/fmod/character_quality_*.fsb`, whose `FmodSoundDefBundle.fsbLoadedHandler` side effect leaks an item in `GamePage.monitor`. `ScenePage.handleLoaded()` then never re-fires, `doInitReady()` → `setReady()` never runs, the local `POST /services/battle/ready` is never sent, and `BattleStateInit` hangs forever. Workaround patch drafted in **Banner-Saga-Factions/BSF-Client#7** (15s timeout in `BattleStateInit` that force-calls `setReady()`) — not applied because it requires rebuilding the SWF. Production 1v1 between two machines does not appear to trigger this — both clients get real FMOD and either both race or both dodge it.
- **`/battle/killed` counts a death only after BOTH clients report it.** Each client independently reports every kill — its own units dying *and* the opponent's (confirmed by captures `0409_c`/`0432_c`). `Battle.applyKillReport()` tracks a per-entity bitmask keyed by `killedparty` and removes a unit from `aliveUnits` only once every `party_index` has reported it (`bits === killMask`), so one modified client can't fabricate the opponent's losses (#18). The winner is then **server-derived** as the party still holding units — never `req.body.killerparty` (#19). Ported from `BattleMonitor.PartiesKills`. Escape hatch: `BSF_KILL_CONFIRM_SINGLE=true` confirms on the first report. Don't "fix" a test that sends one `/killed` and expects the unit gone — it now needs reports from both sessions (`confirmKill` in `test/helpers.ts`).
- **Never edit the per-unit `stats` inside the `defs[]` sent with `BattleCreateData` — they are what BOTH players fight with.** Measured 2026-08-21: one unit's `STRENGTH` and `ARMOR` were rewritten on the wire only (16 → 13 and 8 → 12, both inside the class band so nothing clamped, and both values held by no other unit in the battle), the roster and the server's own battle record kept 16/8, and **both** screens showed 13/12 — including the owning player's. 457 turn boundaries across two runs, zero checksum divergences. Each client builds *both* parties from the payload (`VersusFindMatchState.handleMessage` → `EntityListDefVars.fromJson` → `EntityDefVars.fromJson`), so an edit here rewrites the battle for both sides rather than desyncing them. **Three carve-outs:** `EntityDef.clampStats` pulls out-of-range values back inside the class band (which is why the 2026-06-12 "weak units" run — `STRENGTH=1`/`ARMOR=0`, below every class minimum — read as a no-op); `EntityDef.applyClassStats` fills stats the payload omits from the class table; and that same function **overwrites `ACTIVE_0`, `INJURY` and `INJURY_DAYS` from rank regardless of what we send** (`Stats.addStat` overwrites an existing stat). The roster still decides party membership and turn order, and the client keeps reading it mid-battle for the kill tally and promote-readiness (`SceneStateBattleHandler.onEntityKilled`) — it just supplies no combat number. Offline practice battles differ: they build both sides from the client's own roster. To get short battles for testing, shrink the *party* instead: `/debug/party-limit`. Anything that must really change a unit's strength has to go through the roster (`saveRoster`), not the battle payload. See `docs/client-contract.md` → R13. Client-side mechanism: `bsf-client/docs/data-model.md` §5 "Your account and roster" ([local](../../../bsf-client/docs/data-model.md) | [GitHub](https://github.com/Banner-Saga-Factions/BSF-Client/blob/master/docs/data-model.md)).
- **Crediting a unit's `KILLS` stat (#99) additionally requires both clients to report the same `killer`.** Death confirmation (above) keys on the dead `entity`, not the killer, so it alone wouldn't stop a lone modified client from funneling its confirmed kills onto one favored unit to over-promote it. `applyKillReport()` records the killer the **first** report names (`Battle.killReportKillers`) and only bumps `unitKillCounts[killerparty][killer]` when the **confirming** report names the same killer (a mismatch logs `kill credit skipped: killer mismatch` and credits no one — but the death still confirms, so the battle never stalls). At endgame each side's tally is applied to **its own** roster via `saveRoster`, so a tally can only ever raise the killer-party's own units. **Residual limit:** two *colluding* modified clients can still agree on a false killer — the server can't tell without re-simulating the battle (the same unclosable trust boundary as death confirmation). `BSF_KILL_CONFIRM_SINGLE=true` reverts to trusting the single report's killer.
